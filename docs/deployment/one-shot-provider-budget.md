# One-shot provider budget for homologation

## Failure mode and scope

A Judit acquisition job already has `max_attempts=1` and ambiguous provider failures are terminal, but a retry-safe rejection can be followed by another user request. That means the queue limit alone does not enforce an authorization that permits only one Judit request. A second job can also be delivered independently, so the durable boundary must reserve the call atomically before network I/O.

`JUDIT_MAX_PROVIDER_CALLS` limits outbound Judit acquisition-creation requests (`POST /requests/`) per tenant/process acquisition row. Its default is 100 to retain existing bounded-retry behavior. A one-shot deployment must explicitly set both `PROVIDER_ONE_SHOT_MODE=true` and `JUDIT_MAX_PROVIDER_CALLS=1` in the shared configuration used by the API and both workers, before creating the acquisition row. The API refuses a mismatched mode/limit; the worker verifies both the runtime setting and the persisted row limit before reserving. The same mode constrains Claude to one message.

The worker atomically increments `provider_calls_reserved` before network I/O. A reservation is never refunded, including after an exception, timeout, cancellation, process crash, or explicit rejection. It survives restart. In one-shot mode, `PROVIDER_ONE_SHOT_RUN_ID` is required in API and worker configuration and is bound to the same `approval_id` in the private Claude permit. PostgreSQL's immutable `judit_one_shot_call_reservations` primary key allows at most one Judit reservation across all tenant/process acquisition rows for that run ID; Claude's existing immutable approval ledger allows at most one Claude message for the same ID. The run ID is an authorization reference, not a secret; changing it creates a new budget and requires a new explicit authorization. With limit one, a retry-safe rejection, ambiguous outcome, duplicate task, later explicit refresh, or concurrent request for a different process cannot issue a second Judit creation request for that run. A timeout after reservation leaves the outcome unknown and the budget spent; reconcile using the normal inbound callback or authorized existing evidence, never retry the POST.

In one-shot mode, the central Judit HTTP boundary permits exactly one reserved `POST /requests/` per reservation context. It blocks other Judit HTTP operations—including tracking creation/refresh/deletion, status/response polling, attachment downloads, connectivity probes, and the live-smoke script—before network I/O. The context is consumed before request construction and cannot be reused. Inbound callbacks are not outbound calls. Do not mix the live-smoke tool's separate local marker budget with the PostgreSQL pipeline budget.

## Migration and rollout

Migration `037_judit_provider_call_budget.sql` is additive. Existing rows receive a limit of 100 and a conservative reservation count based on `attempt_number`, because a crash may have happened after provider acceptance but before saving the returned request ID. This backfill is a transactional table-wide update; inspect acquisition-table size and schedule an appropriate maintenance window before applying it. A check constraint prevents the counter from exceeding the stored limit; a trigger prevents refunding reservations, expanding the row limit, or moving the reservation timestamp backward. The migration also blocks deletion of Anthropic reservation rows: otherwise a reused approval ID could reset its durable message budget. This enforces the nonrenewable approval contract, not an absolute billing ceiling. The global run table stores only the run reference, timestamp, and a foreign-key link to the existing acquisition row; it adds no tenant ID, CNJ, or provider payload. The link uses `ON DELETE SET NULL`, preserving the consumed run tombstone if the acquisition row is deleted. The current scheduler expunge deletes process rows and Judit payloads but does not delete `tenant_judit_requests`; that existing retention behavior is unchanged here, so the link can remain until the acquisition row is separately removed. Verify the intended acquisition-row retention policy before production rollout.

The old application ignores the new columns and does not contain the one-shot HTTP gate, so it cannot enforce this budget. Before migration, disable provider egress/credentials and drain old workers; do not run old workers with provider access while the migration or new rollout is in progress. The migration service also reruns `scripts/provision_db_roles.py`: the API receives read-only access to the global budget table and workers receive only SELECT/INSERT. Roll out one immutable image digest to API and all workers as a unit, apply the additive migration and role provisioning first, and do not allow an old worker to run while provider egress/credentials are enabled.

The permanent database guardrails encode the explicit homologation decision of at most one Judit request and one Claude message per approved run; they do not demonstrate legal acceptance or an external billing ceiling. The Anthropic delete guard also enforces the existing non-reuse contract in `docs/release/ragvia-02b-preacceptance.md`. Revisit either guard only if Rpy adopts a documented, auditable approval-revocation/renewal lifecycle with tests; otherwise a new authorized run requires a new run reference. Before any application rollback, disable Judit and Anthropic credentials/egress, stop and drain workers, then roll back the image; retain the migration columns and reservation data. Do not drop or rewrite the migration. The deployment environment validator must pass with one-shot settings; the image digest must be identical across API, workers, scheduler, and migration job. Never inspect expanded Compose output because it may contain secrets.

The per-row limit is captured when the tenant/process row is first created. Do not pre-create the acquisition under the default limit and then assume setting the environment to `1` lowers that existing row. The global run reservation is independent of row creation and atomically limits the whole authorized run. For an exhausted per-row or global budget, the API returns HTTP 409 without enqueuing another provider request.

## Claude one-message control

The private Claude approval must match the authorized tenant/process/version, the exact `PROVIDER_ONE_SHOT_RUN_ID`, and exact model, with `max_regenerations=0` (one message total). Before the Claude reservation is committed, PostgreSQL also verifies that this run's Judit acquisition produced the exact current version for the authorized tenant/process. In `PROVIDER_ONE_SHOT_MODE`, the loader rejects a mismatched run ID or any nonzero regeneration allowance; the ordinary non-one-shot policy remains unchanged. Configure `ANTHROPIC_MODEL=claude-sonnet-4-6`, `PROVIDER_MAX_ATTEMPTS=1`, and `PROVIDER_RETRY_BACKOFF_SECONDS=0`; the SDK is constructed with `max_retries=0`. The generation permit remains disabled unless the private approval and explicit paid-generation gate are both valid. These settings are not authorization by themselves. The second application-level validation generation and any local retry are blocked before a second network call.

The one-shot deployment validator also requires the local BGE embedding runtime, with external embeddings, reranking, DataJud, and Judit attachments disabled, so the homologation does not silently spend other provider calls. The private approval is still validated by `load_generation_permit` at generation time; the environment validator does not prove the provider account's external spend limit.

## Evidence and limitations

`tests/integration/test_tenant_process_request_postgres.py` verifies atomic per-row and global-run reservation (including concurrent different processes), retry-safe rejection, ambiguous failure, timeout, task restart, and non-refundable/non-expandable budget triggers with PostgreSQL. `tests/test_judit_one_shot_mode.py` verifies the HTTP boundary allows one reserved request-creation POST and blocks alternate Judit operations before network I/O. These tests patch provider I/O and are synthetic evidence only; they do not establish live Judit compatibility. Claude authorization tests verify a single durable message, including timeout/restart behavior. No provider call is required for these checks.

This mechanism does not establish tenant authorization or capture provenance. Do not create an acquisition until the authorized tenant/capture link is independently documented. A later live run still requires a verified Judit credential, a secure Anthropic credential, approved generation permit, confirmed capture provenance, a deployed image containing this migration and code, and the explicit one-call authorizations.

## Credential rotation and Windows ACL procedure

The inspected developer `.env` had inherited ACLs, including `Authenticated Users: Modify` and `BUILTIN\\Users (SID S-1-5-32-545): ReadAndExecute`. Treat its Anthropic credential as exposed; do not read, copy, print, or reuse it. Confirm it is not the active deployment source, rotate/revoke it through the Anthropic console, and verify service configuration by presence/status only. If it is active, coordinate a controlled secret replacement before revocation; never put the new value in Git, tickets, logs, screenshots, or Compose output.

Prefer a managed secret store. If a host file is unavoidable, create a dedicated secret directory and file with inheritance disabled; grant read only to the deployment operator and full control only to SYSTEM/Administrators. Protect the directory as well as the file, because directory write access can permit replacement. Verify ACL metadata with `Get-Acl`/`icacls` only; do not use `Get-Content`, `type`, `Select-String`, or commands that print environment values. Do not harden the existing `.env` in place until its active consumers and rollback needs are confirmed. After replacement, verify only the credential's presence and provider-side key status without emitting its value, then revoke the old key and remove its old copies under the organization's retention policy.
